# 分层残差编码与快速上屏设计（layer 模式）

> 线格式契约见 [protocol.md](protocol.md) §3.4/§5；选型实验见
> [layer_test_report.md](layer_test_report.md)；总体方案见
> [android_client_plan.md](android_client_plan.md)。

## 1. 问题与目标

单流 H.264 投屏的时延-画质耦合：画质要高就得码率大、单帧大，链路一抖
（热点/弱网）就积压卡顿；码率压低保流畅，则文字/彩边发虚。

layer 模式把画质拆成**两层解耦**：

- **基础层**（ch 0）：低码率 single 几何 H.264（886×1920 BT.601 4:2:0），
  可独立解码上屏——它是"必达的低保真画面"，链路再差也有东西看。
- **增强层**（ch 4）：基础层重建与原始帧之间的**残差**，第二个硬件编码器
  编码——它是"可丢弃的增值"，赶上上屏窗口就合成出近原图画面。

上屏语义：**两帧赶上上屏 → 解码后合成；赶不上 → 上屏低码率基础帧**。
增强层的迟到/丢失永远不阻塞基础层。

## 2. 残差编解码机制

### 2.1 残差定义

```
sym[i] = clamp(orig[i] − recon[i], −128, 127) + 128      ∈ [0,255]，128 = 零残差
```

- `orig`：采集帧打包成的 single I420（Y W×H + U/V (W/2)×(H/2) planar）
- `recon`：基础层码流的**解码重建帧**（见 §2.2 闭环）
- 钳制到 ±128 以外的残差有损失（实测 H.264 重建误差几乎不越界）

### 2.2 闭环：残差必须相对"对端的重建"计算

客户端合成的是 `client_recon + sym`。若残差相对原始帧计算，两端解码器
实现的细微差异会让合成结果漂移。H.264 解码是**逐字节确定**的（实测
oneVPL(host) 与 MediaCodec(小米) 对同一码流重建 0 字节差，
[layer_test_report.md](layer_test_report.md) §2），因此 server 端用
**BaseDecoder 本地闭环解码自己的输出码流**，得到与 client 完全一致的
recon，残差 = orig − recon 才严格成立。

```
虚拟显示 → RGBA → repack(single I420) ──→ 基础编码器 ──→ ch 0 即发（低时延）
                  │                          │
                  │ orig 留底                └→ BaseDecoder 闭环解码（本地）
                  │                          ↓ recon
                  └──────→ compute_residual（sym = orig − recon）
                                    ↓
                          EnhEncoder（第二个 MediaCodec 硬编）→ ch 4
```

### 2.3 为什么残差帧"直接"送硬件编码器（直偏置，不熵编码、不差分伪装）

残差 sym 平面本身就是一张"近灰噪声图"：大面积 128 常数（零残差平坦区，
H.264 帧内 DC / 帧间 skip 几乎不耗比特）+ 小幅值量化噪声。恰在通用硬件
编码器的舒适区。实测（[layer_test_report.md](layer_test_report.md)）：

| 方案 | 体积/帧 | 结论 |
|---|---|---|
| Rice 无损熵编码（kind=0x01，对照保留） | ~1.4MB | 无损但太大 |
| 差分伪装（方案A：水平差分+偏置） | 423K~1.25MB | ❌ 白噪声差分放大高频（6~21×）且前缀和行内误差累积，PSNR 崩到 9dB |
| **直偏置 + H.264 硬编（kind=0x02，采用）** | 34K~170K | ✅ 把 28.35dB 基础层补到 29.6~34.57dB |

增强编码器配置：帧间预测（静止期残差高度相似，帧间收益大）+ 周期 IDR 1s
+ 码率 = capacity × (1 − base_share)（tight video_capacity 回调驱动，
与基础层 base_share 互补分配）。

### 2.4 双参考链与独立恢复

两条独立的 H.264 流各有自己的参考链、门控和恢复通道，**断链互不染**：

| | 基础层（ch 0） | 增强层（ch 4） |
|---|---|---|
| FEC | 开（自适应+起始保护） | **关**（校验片带宽让给基础层；丢包即弃不上屏） |
| ARQ | 关（重传乱序断链） | 关 |
| 断链检测 | tight 丢帧回调（ch 0） | tight 丢帧回调（ch 4）/ 乱序 / 解码失败 |
| 恢复命令 | 0x05 REQ_KEYFRAME | 0x07 REQ_ENH_KEYFRAME（1.5s 节流） |
| 编码器保障 | MIUI 忽略同步帧 → >2.5s 无 IDR 整体重建 | 同左（2.5s 兜底重建） |

### 2.5 线格式（ch 4，tag 0x57）

```
[0]    u8   tag = 0x57
[1..8] u64  pts_ms        —— 与同帧基础消息一致（配对键）
[9]    u8   kind = 0x02   —— H.264 直偏置残差帧（0x01 = Rice 对照）
[10]   u8   enh_flags     bit0 = 增强流 IDR
[11..]      H.264 Annex-B AU（IDR 前拼增强流自身 SPS/PPS）
```

## 3. 快速上屏机制（client）

### 3.1 配对与门控

- 配对键 = pts_ms；增强层残差解码完成即入小 map（cap 4，挤最旧）。
- 迟到即弃：pts ≤ 已上屏 pts 的残差直接丢（对应基础帧已上屏，无法回溯）。
- 双门控独立：`got_idr`（基础）/ `enh_got_idr`（增强）；任一断链即
  **清空残差 map**——断链期算出的残差与重建链不一致，挂上必闪色。

### 3.2 保序全解码（不做"顶帧拒收"）

帧一律提交解码器**推进参考链**；丢弃只发生在已解码帧（DisplayScheduler
队满丢最旧留最新）。拒收未解码的 P 帧会断参考链并引发关键帧风暴——
早期版本的做法，已修正。

### 3.3 grace 窗口：合成命中率的前提

增强层固有滞后 = 基础闭环解码 + 残差计算 + 增强编码 ≈ 50~150ms。
基础帧若到即上屏（零等待），增强层**永远赶不上**。因此解码帧入队后留
grace 窗口（默认 150ms，`enhWaitMs` 可调）：

- 窗口内同 pts 残差就绪 → 纹理域相加合成（`clamp(base+sym−128)`）上屏
- 窗口到期仍未就绪 → 上屏低码率基础帧（不继续等）

### 3.4 P50 自适应 grace：只覆盖偶发延迟

grace 取固定值的陷阱：系统性小于实际滞后会**退化成永远基础帧上屏**，
系统性太大又白加时延。故持续测量增强到达滞后（ch4 到达时刻 − 同 pts
ch0 到达时刻），滑窗 120 样本、每 30 样本重估：

```
grace = clamp(P50(lag) + 30ms 余量, 0, 300ms)   （变化 >20ms 才调整，防抖）
```

P50 覆盖"正常 + 偶发偏慢"的一半场景按时合成；系统性迟到超 300ms 不硬等
（交给 §3.5 兜底），网络转好后 grace 自动回落。

### 3.5 饿死兜底：模糊 > 冻屏

新帧断流（内容静止/网络抖动）且队列里没有成熟帧时，若画面已停滞
≥ grace，则提前上屏队列中**最新**的基础帧——被跳过的是已解码旧帧，
不断参考链；基础帧模糊是暂时劣化，冻屏是故障。

## 4. 实测（小米 10 热点 + 华为 NOH-AN00，886×1920）

| 指标 | 实测 |
|---|---|
| 合成命中率 | 53~62%（grace=150ms 初值，P50 自适应后随链路浮动） |
| 双解码器 | dec0/dec1 fed≈out（Java MediaCodec buffer 模式，华为 EMUI） |
| server 增强管线 | baseDecOut ≈ enhComputed ≈ enhSent（全链路流通） |
| 残差计算 | ~8-9ms/帧（SD865 native） |
| 增强编码 | 稳态 ~10ms 级/帧（实验冷启动数据见报告） |

## 5. 已知限制与后续

- 合成为近似无损（增强层 H.264 有损）；|残差| > 128 的极端块被钳制。
- layer-double（基础层 double 几何、4:4:4 残差）协议位已预留
  （mode `0b110`），未实现。
- Rice 无损对照路径（`--enh-impl rice`）保留，kind=0x01。
- 残差纹理分配教训（首残差帧与基础帧同尺寸时 glTexSubImage2D 写未分配
  纹理 → 闪色）：纹理生命周期必须独立于基础帧尺寸跟踪。
